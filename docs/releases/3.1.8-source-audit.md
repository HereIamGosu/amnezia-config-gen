# Release 3.1.8 — Source Audit

Checked on 2026-11-01 from `e0ef1bc` (3.1.7 plus its ledger commit). No upstream source was read: the release changes how the server answers a failed Cloudflare WARP registration and what it builds from a registration without IPv6; the WireGuard/AmneziaWG wire format, AWG profiles, CPS, `vpn://` and Endpoint Lab are untouched. The protocol evidence of [3.1.0](3.1.0-source-audit.md) is unchanged; `npm run evidence:check` is part of the release checks.

## Protocol surface

For a registration answer with a valid IPv6 address nothing in the `.conf` text, its field order, AWG parameters, `I1`–`I5`, `vpn://` or the response fields changes. Checked against `v3.1.7` on the local oracle stand (real handler, fake Cloudflare registration, the 68 parameter sets of 3.1.7, 8 runs each, `.conf` structure and fixed fields): no set differs. `Jc`/`Jmin`/`Jmax` with `router=1` are random on both sides and would have been allowed to differ; they were also checked against the router bounds on 1000 router configs (all four modes; `router`, `mobile+router`, `count=3`): `Jc ≤ 2`, `40 ≤ Jmin ≤ 64`, `Jmin + 64 ≤ Jmax ≤ 128`, none out of bounds.

The new path, a registration without a usable IPv6 address, gives the config of `ipv6=0` for the same request: only `Address` and, with `ipv6=1`, `AllowedIPs` differ from the config of an answer with IPv6 (`__tests__/warp-ipv4-degradation.test.js`, field by field in all four modes). `S1–S4 = 0`, `H1–H4 = 1..4`, `MTU = 1280`, the AWG 2.0 field order and `I1` hold (I1–I5); the router caps hold with `router=1` and `mobile=1&router=1` in every config of `count=3` (I8); `mobile=1` gives the same config as with IPv6 (I7); the Lab endpoint stays (I11); `vpn://` carries the same `.conf` (I10). I6 gains the sentence "a registration without an IPv6 address gives the IPv4-only config, also with `ipv6=1`" (README, `__tests__/invariant-i6-ipv4-default.test.js`). No invariant is weakened.

## The request to Cloudflare

The registration code moved from `api/warp.js` to `src/server/warpRegistration.js`. Profile `legacy` only. The requests are unchanged: `POST /v0i1909051800/reg` with `{"install_id":"","tos":…,"key":…,"fcm_token":"","type":"ios","locale":"en_US"}`, `PATCH /v0i1909051800/reg/{id}` with `{"warp_enabled":true}`, `GET /v0i1909051800/reg/{id}`; host `api.cloudflareclient.com`, port 443, `agent: false`, headers `Content-Type: application/json`, `User-Agent: okhttp/3.12.1`, `Authorization: Bearer …` after `POST`, `Content-Length`, in this order. `__tests__/warp-registration-request.test.js` asserts each of these; changing the user agent, the header order, `agent: false` or the registration `type` makes it fail (checked by mutation). The timeout timer of `httpRequestOnce` is armed after `https.request`, the order of 3.1.7: moving it back makes the two tests of 3.1.7 finding 1 in `__tests__/unhandled-rejection-audit.test.js` fail (checked by mutation on the move commit and on the final tree).

## Failure classes

Every error thrown inside the registration module carries `source: 'cloudflare'`, `registrationClass`, `upstreamStatus` and `retryAfterS`. The handler checks `labCode`, then `registrationClass`, then the old `statusCode` logic, so local refusals (`cps_chain_*`, unknown presets, `warpPort`, Lab Auto) answer as before. The table of answers is in [3.1.8.md](3.1.8.md). The retried outcomes are those of 3.1.7; `isTransientApiFailure` reads the Cloudflare code from `upstreamStatus` instead of `statusCode`, its lists are unchanged. `Retry-After` is read only as `res.headers?.['retry-after']` (the test fakes answer without headers). A synchronous refusal of `https.request` (an `id` or `token` Node cannot send) becomes `malformed` in `handleApiRequest`, so `httpRequestOnce` itself behaves as in 3.1.7. `id` and `token` must be non-empty strings before `PATCH`; Cloudflare's are strings, and a non-string value used to reach the request path as text.

Checked by mutation on `__tests__/warp-registration-errors.test.js`: 501 as `unavailable`, 408 as `rejected`, Cloudflare's `Retry-After` ignored, the 3600 s bound dropped, the retry list reading `statusCode`, Cloudflare's text in the answer, the class check skipped, a non-string `id` accepted — each fails the test.

## Outcome counters

One outcome per registration (`ok`, `ok_ipv4_only`, `rate_limited`, `unavailable`, `rejected`, `malformed`) in the memory of the process; a line `[warp-registration-stats] window=600s profile=legacy …` every 10 minutes when the window had a registration, and from `shutdown` in `server.js`. The window timer is `unref()`. The line holds numbers and the profile name only (`__tests__/warp-registration-stats.test.js`, `__tests__/secret-leakage.test.js`). No request is added.
