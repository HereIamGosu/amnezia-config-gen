# AmneziaWG Config Generator 3.1.7

## Router caps in Legacy, IPv4-only split routes, a timer that could stop the server, texts

Prepared on 2026-10-31 after 3.1.6 (`6ce721a`). Production has served the generation changes below since 2026-10-31 (`d4dc402`); this release gives them a version and a tag.

## What changed for users

**Router configs.** With `router=1` a Legacy config kept its template junk (`Jc = 120`, `Jmax = 911`), although the router option promises `Jc ≤ 2` and junk up to 128 bytes. The caps now apply in every mode, after the mobile preset. `Jmin` is capped at 64 and `Jmax` stays between `Jmin + 64` and 128: before, about nine in ten router configs got `Jmin = Jmax = 128`, so every junk packet had the same size.

**Split-tunnel routes.** When the IP list service put an IPv6 entry into its IPv4 answer, that entry reached `AllowedIPs` of a desktop config without `ipv6=1`. It is now dropped when the answer is read.

**Texts.** The hint under the number of configs promised "variants with different endpoints"; standard WARP templates give every config the same `Endpoint` hostname, and what differs in every mode is the keys. It now reads "Generate 1–3 configs with different keys". Fifteen Russian strings of Endpoint Lab, the result summary and the status block that were left in English are translated, in the dictionary and in the static markup of the Russian pages. The English Lab step "Tunnel WARP" reads "WARP tunnel", as in the check list.

**English app.** `/en` links its own manifest (`/en/site.webmanifest`: start URL `/en`, language `en`, English description) instead of the Russian one, whose start URL is `/`.

**Discord.** The READMEs, `SECURITY.md`, `CODE_OF_CONDUCT.md`, the issue template and `/.well-known/security.txt` now give the same invite as the site.

## The server and failing external services

An audit of promises nobody waits for (`3.1.7-source-audit.md`) went through `api/`, `src/server/` and `server.js`. One defect could stop the process: when a Cloudflare registration answer carried an `id` or `token` that Node refuses in a request path or header, the follow-up request failed at once (the visitor got HTTP 500, as before), but its 20 s timeout timer stayed armed and then threw outside any handler. Node ends the process on such an exception, which drops every request in flight until the container restarts. The timer is now armed only after the request exists; the opencck, community list and antifilter fetchers, where Node cannot refuse the request today, follow the same order.

Whether this path ever fired in production is not known; the fix closes it, it does not answer an incident.

Every external source now fails in a test (refusal, timeout, non-JSON), and `server.js` runs once with the network cut off: each path answers with a status and a JSON body, and no promise rejection goes unhandled. No global `unhandledRejection` handler was added (owner decision): one that logs and carries on would hide defects of this kind.

## AWG profiles and the API

The `.conf` changes are those above: router caps in Legacy and the `Jmin`/`Jmax` bounds with `router=1` (I8), no IPv6 entry from the cidr4 answer without `ipv6=1` (I6). No new parameter, field or error code; the answer to a failing Cloudflare call is unchanged. Invariants I1–I11 are not weakened.

## Evidence boundary

- Generation was compared with `v3.1.6` on the local oracle stand (real handler, fake Cloudflare registration, 68 parameter sets × 8 runs, `.conf` structure and fixed fields): every difference is in Jc/Jmin/Jmax of a set with `router=1` (how many of those sets differ changes from run to run, because the 3.1.6 values are random). Those fields were checked against the bounds instead: 1000 router configs (all four modes; `router`, `mobile+router`, `count=3`) all had `Jc ≤ 2`, `40 ≤ Jmin ≤ 64`, `Jmin + 64 ≤ Jmax ≤ 128`. The stand does not cover split tunnelling with presets or the `vpn://` payload; the IPv6 filter is shown by the test "I6: the opencck stage stays IPv4-only by default".
- The timer defect is shown by tests with a fake `https.request` that refuses values exactly as Node does (anchored by a test against Node's own `http.request`) and mocked timers; no real Cloudflare answer with such an `id` or `token` was seen.
- No WARP registration was made for this release.
- A POST to `/api/warp` with `Content-Type: application/json` and an empty body still waits for the 60 s deadline (504); it does not crash and is left for a later release.
