# AmneziaWG Config Generator 3.2.3

## «Подключилось?» answers tied to the generation they are about

Prepared on 2026-11-14 after 3.2.2 (`7f412b4`). Nothing changes on the page for visitors, and config generation does
not change: the server code (`api/`, `src/`, `server.js`) is that of 3.2.0.

## What changed

**Answers are attributable.** Yandex Metrica keeps goal parameters per visit, without the goal name. In the first week
after 3.2.2 (2026-11-08…11-13) visits with a «Нет» answer held 4.2 successful generations on average: people followed
the steps and generated again, and the profile and endpoint of the answered config were mixed with those of every other
generation of the visit. `connection_works`, `connection_fails` and `connection_next_step` now send their fields under
the event name:

```js
ym(99328227, 'reachGoal', 'connection_fails', { connection_fails: { mode: 'awg3', endpoint_mode: 'lab', … } })
```

so a report reads them as `paramsLevel1 = connection_fails`, `paramsLevel2 = mode`, `paramsLevel3 = awg3`.

**Two more fields in an answer:** `route_mode` (`full` or `split`) and `attempt`, the number of the successful
generation in the browser tab (1, 2, 3…; kept in `sessionStorage` across `/` ↔ `/en`, counted in memory without it).

All other events keep their flat parameters, so earlier reports and goals read them as before. The events, the Metrica
goals and their IDs do not change. No keys, addresses, presets or text: every value still passes the allowlist of
`public/static/analytics.js`.

## Evidence boundary

The reports of 2026-11-14 show visit parameters as a tree (`paramsLevel1` = key, `paramsLevel2` = value for flat
parameters); that a nested object adds a third level is expected from that tree but not yet seen in a report on this
release. It is checked after deployment with a filter on `ym:s:paramsLevel1=='connection_fails'`. No WARP registration
was made for this release.
