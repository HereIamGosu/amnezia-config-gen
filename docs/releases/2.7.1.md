# AmneziaWG Config Generator 2.7.1

## Корректирующий релиз AWG 3.0/3.1 для Cloudflare WARP

Версия 2.7.1 завершает повторный технический аудит поддержки AWG 3.0 и 3.1, появившейся в 2.7.0. Поводом стали замечания после закрытия Issue #4: первоначальная реализация правильно защищала соединение с обычным WireGuard peer от несовместимых AWG-механизмов, но оказалась слишком консервативной для двух параметров, которые не требуют согласованной настройки на стороне Cloudflare.

В результате:

- `ContentPaddingAddition = 10-100` включён по умолчанию в AWG 3.0 и AWG 3.1;
- AWG 3.1 по умолчанию получает `DisableCookies = on`;
- оба параметра можно явно отключить;
- `RandomTrailers` и `HeaderProtectionKey` по-прежнему невозможно включить для WARP;
- все числовые диапазоны AWG 3.x проверяются по публичному `.conf`-контракту `uint16`, то есть `0..65535`;
- API, результирующие метаданные, интерфейс и документация теперь описывают один и тот же фактически сгенерированный профиль.

Это patch-релиз с намеренным изменением defaults для AWG 3.x. Legacy WireGuard и AWG 2.0 не затронуты.

## Коротко: что изменится для пользователя

При обычной генерации AWG 3.0 интерфейс теперь содержит:

```ini
[Interface]
MTU = 1280
S1 = 0
S2 = 0
S3 = 0
S4 = 0
H1 = 1
H2 = 2
H3 = 3
H4 = 4
ContentPaddingAddition = 10-100
RekeyAfterTime = 100-120
RekeyTimeout = 3-7
RejectAfterTime = 150-180
KeepaliveTimeout = 5-15
MaxHandshakeAttempts = 15-20
PersistentKeepalive = 25-35
```

AWG 3.1 дополнительно содержит:

```ini
RandomTrailers = off
DisableCookies = on
```

Значения `PrivateKey`, `Address`, DNS, CPS, junk-параметры, endpoint, peer key и маршруты в примерах опущены. Они продолжают формироваться обычным способом.

## Почему понадобился 2.7.1

Релиз 2.7.0 исходил из безопасного правила: если Cloudflare не понимает AWG-параметр, параметр нельзя добавлять в WARP-конфигурацию. Само правило остаётся правильным, но после изучения полного send/receive path выяснилось, что его применили слишком широко.

Параметры AWG делятся не просто на «поддерживается Cloudflare» и «не поддерживается». Для совместимости важен механизм:

1. Параметры, меняющие распознавание handshake или требующие общего секрета, должны совпадать на обеих сторонах.
2. Локальные таймеры, генерация junk/CPS и локальные решения принимающей стороны не требуют знания значений удалённым peer.
3. Некоторые параметры меняют исходящий transport payload, но результат всё равно остаётся корректным входом для стандартной WireGuard реализации.

В 2.7.1 каждый спорный параметр проверен по актуальному исходному коду, а не по одному успешному импорту, первому handshake или поведению стороннего генератора.

## Технический разбор `ContentPaddingAddition`

### Что делает параметр

`ContentPaddingAddition` добавляет случайное количество нулевых байтов к внутреннему IP-пакету перед его шифрованием как WireGuard transport data. Например, диапазон `10-100` означает, что реализация выбирает допустимое добавление в пределах от 10 до 100 байтов с учётом доступного UDP window.

### Почему Cloudflare не должен знать диапазон

Последовательность отправки выглядит так:

1. Формируется обычный IPv4 или IPv6 packet.
2. К plaintext добавляется content padding.
3. Весь plaintext вместе с padding передаётся в AEAD `Seal`.
4. Удалённый WireGuard peer выполняет обычный AEAD `Open`.
5. После расшифрования длина реального IP-пакета определяется по IPv4 `Total Length` или IPv6 `Payload Length`.
6. Байты после объявленной IP-длины отбрасываются.

Padding аутентифицирован шифрованием, но не является отдельным handshake-расширением и не требует конфигурационного значения на принимающей стороне.

### Ограничения

Это не означает, что произвольный огромный padding безопасен для каждой сети. Он расходует доступное место в UDP datagram и способен ухудшить throughput или увеличить риск фрагментации. Генератор сохраняет WARP MTU `1280` и консервативный официальный default `10-100`, однако поведение конкретного path MTU требует реального сетевого теста.

### Политика 2.7.1

- AWG 3.0: default `10-100`.
- AWG 3.1: default `10-100`.
- Допустимы одно число или диапазон `min-max`.
- Минимум и максимум: `0..65535`.
- `off`, `0` и `0-0` удаляют поле из результата.
- Обратный диапазон, лишние символы, перенос строки и значение `65536` отклоняются HTTP 400.

## Технический разбор `DisableCookies`

### Что именно отключается

В AWG receive path флаг проверяется перед локальной веткой, которая при высокой нагрузке:

- проверяет MAC2;
- применяет rate limiter;
- при необходимости формирует исходящий Cookie Reply.

При `DisableCookies = on` эта локальная защитная ветка не выполняется.

### Что не отключается

Обработка входящего Cookie Reply сохраняется. Форматы Handshake Initiation и Handshake Response не меняются, общий секрет с Cloudflare не появляется, а удалённый peer не обязан иметь такой же флаг.

### Security trade-off

`DisableCookies=on` следует рассматривать как anti-fingerprinting настройку, а не как улучшение безопасности. Она уменьшает различимость локального AWG-поведения, но одновременно отключает часть локальной cookie-based anti-DoS защиты под нагрузкой.

### Политика 2.7.1

- Доступно только для AWG 3.1.
- Default: `on`.
- Явно принимаются `true`, `1`, `on`, `false`, `0`, `off`.
- Произвольные строки отклоняются HTTP 400.
- Попытка использовать параметр в AWG 3.0 отклоняется HTTP 400.
- При `off` конфиг честно содержит `DisableCookies = off`, а metadata не объявляет feature включённой.

---

## Почему `RandomTrailers` по-прежнему выключен

`RandomTrailers` добавляет дополнительные байты после handshake initiation, response или cookie packet. В AWG receive path пакет увеличенного размера принимается только тогда, когда локальная сторона также разрешила random trailers и умеет обрезать datagram до фиксированного размера соответствующего WireGuard message.

Обычный WireGuard peer ожидает стандартный размер handshake datagram. Cloudflare нельзя настроить на AWG receive path, поэтому включение trailers остаётся peer-dependent изменением wire format.

Дополнительная ловушка: размер trailer зависит от изученного `peer.udpWindow`. В начале соединения добавление может оказаться нулевым, а после накопления состояния или rekey — стать ненулевым. Поэтому сценарий «импортировалось и первый handshake прошёл» не доказывает стабильную совместимость.

Политика 2.7.1:

- AWG 3.1 всегда выводит `RandomTrailers = off`;
- AWG 3.0 не включает механизм;
- GET/POST override со значением `on`, `true` или `1` отклоняется до регистрации WARP;
- default, template, mobile, router и multi-config пути проходят один финальный safety layer.

---

## Почему `HeaderProtectionKey` по-прежнему запрещён

Header protection применяется при отправке и снимается при приёме. Для правильной классификации и восстановления заголовка обе стороны должны использовать совместимый ключ и связанные параметры padding/header ranges.

Cloudflare не предоставляет способ установить этот ключ для WARP peer. Поэтому генератор:

- никогда не выводит `HeaderProtectionKey`;
- отклоняет попытку передать его через GET или POST;
- не предлагает UI-переключатель;
- не допускает обход запрета через шаблон или composition path.

## API: совместимость и новые правила

### Режимы

Канонические значения сохраняются:

- `mode=awg3`;
- `mode=awg31`.

Существующие aliases и шаблоны продолжают нормализоваться в эти режимы.

### Content padding

```text
GET /api/warp?mode=awg31&contentPaddingAddition=12-64
```

```json
{
  "mode": "awg31",
  "contentPaddingAddition": "off"
}
```

`experimentalContentPadding=true` не удалён и не вызывает ошибку, но больше не нужен. Он сохранён только для обратной совместимости старых интеграций.

### Disable cookies

```text
GET /api/warp?mode=awg31&disableCookies=off
```

```json
{
  "mode": "awg31",
  "disableCookies": true
}
```

### Диапазоны

Следующие поля используют строгую проверку `0..65535`:

- `contentPaddingAddition`;
- `persistentKeepalive`;
- `rekeyAfterTime`;
- `rekeyTimeout`;
- `rejectAfterTime`;
- `keepaliveTimeout`;
- `maxHandshakeAttempts`.

Допустимы `N` и `min-max` без пробелов. Для content padding и persistent keepalive также доступны disable-формы.

### Ошибки до регистрации

Невалидный AWG 3.x параметр возвращает `success=false` и HTTP 400 до внешнего запроса регистрации. Это предотвращает расход rate limit Cloudflare на заведомо некорректный запрос.

## Метаданные результата

Поле `awg.enabledFeatures` теперь строится из реально сгенерированного конфига:

- содержит `content-padding-addition`, только если поле присутствует;
- содержит `disable-cookies`, только если AWG 3.1 действительно использует `on`;
- никогда не объявляет `random-trailers` или header protection включёнными.

`awg.experimentalFeatures` больше не содержит content padding. Это соответствует новому статусу функции после source audit.

UI на русском и английском использует ту же модель. Карточка результата не обещает поддержку функции, которой нет в скачанном конфиге.

## `.conf`, `vpn://` и версии клиента

### AWG 3.0

AWG 3.0 остаётся `.conf`-only. В актуальном `amnezia-client` все обнаруженные AWG v3 markers классифицируются как `awgV3`, а строковое значение `awgV3` равно `3.1`. Независимое историческое значение `protocol_version` для AWG 3.0 не подтверждено исходным кодом.

Генератор не подставляет выдуманный protocol version ради получения ссылки.

### AWG 3.1

Для AWG 3.1 `vpn://` использует подтверждённое значение `protocol_version=3.1`.

### Клиенты

Для импорта AWG 3.x требуется актуальная версия AmneziaVPN или AmneziaWG с поддержкой AWG 3.1-полей. Обычный WireGuard клиент не обязан понимать дополнительные строки AWG в `[Interface]` и не считается поддерживаемым импортёром такого файла, даже если удалённый Cloudflare peer остаётся stock WireGuard.

Версия клиента, способ упаковки конфигурации и совместимость удалённого peer — три разные вещи.

## Mobile, router, templates и несколько конфигураций

Финальная WARP safety-проверка применяется после композиции параметров. Поэтому одинаковые ограничения действуют для:

- обычной генерации;
- шаблонов AWG 3.0/3.1;
- mobile profile;
- router profile;
- IPv4 и IPv6 вариантов;
- CPS5;
- `count=1..3`;
- GET и POST.

Ни один из этих путей не может случайно вернуть `RandomTrailers=on`, HeaderProtectionKey или изменённые S/H значения.

## Безопасность и модель угроз

Релиз сохраняет следующие правила:

- приватные ключи остаются только в сгенерированных конфигурациях и не попадают в compatibility metadata;
- сообщения об ошибках не должны включать `.conf`, `vpn://`, WARP token или private key;
- строгий parser отклоняет переносы строк и попытки внедрения дополнительных INI-полей;
- peer-dependent поля нельзя включить скрытым query parameter;
- WARP registration rate limiting остаётся активным;
- `DisableCookies=on` явно описан как компромисс локальной anti-DoS защиты.

Перед публикацией diff отдельно проверяется Gitleaks.

- Старые запросы без новых параметров.
- `experimentalContentPadding=true`.
- Timing overrides 2.7.0.
- AWG aliases и templates.

```text
?mode=awg31&contentPaddingAddition=off&disableCookies=off
```

При этом `RandomTrailers` всё равно останется выключенным, а HeaderProtectionKey — недоступным.

## Диагностика

### Файл не импортируется

1. Убедитесь, что используется актуальная AWG 3.1-capable версия клиента.
2. Для AWG 3.0 импортируйте `.conf`, а не ожидайте `vpn://`.
3. Проверьте, что файл не открывается обычным WireGuard клиентом вместо AmneziaWG.

### Импорт успешен, но handshake отсутствует

1. Проверьте доступность выбранного UDP-порта WARP.
2. Сравните с baseline без content padding и с `DisableCookies=off`.
3. Убедитесь, что в конфиг вручную не добавлены HPK, trailers или изменённые S/H.
4. Проверьте системное время и endpoint.

### Первый handshake есть, позже соединение пропадает

Такой сценарий особенно важен для проверки peer-dependent механизмов. Зафиксируйте время сбоя относительно `RekeyAfterTime`, дождитесь минимум одного rekey и повторите тест без пользовательских правок конфига.

### Handshake есть, но сайты не открываются

Проверьте DNS, `AllowedIPs`, split-tunnel маршруты, IPv6 и MTU. Отдельно сравните baseline и `ContentPaddingAddition=10-100` на той же сети.

### Работает на Wi-Fi, но не работает в мобильной сети

Сравните доступные WARP UDP-порты и path MTU. Успех на одной сети не доказывает универсальную транспортную совместимость.

## Что автоматические тесты не доказывают

Unit и integration tests генератора доказывают форму конфига, API-контракт, валидацию и невозможность обойти WARP safety layer. Они не заменяют реальное UDP-соединение.

На момент подготовки документа локально не подтверждены:

- реальный Cloudflare WARP handshake для всех вариантов;
- DNS и web browsing;
- large TCP transfer;
- UDP traffic;
- idle period;
- прохождение минимум одного rekey;
- reconnect;
- сравнение Wi-Fi и mobile network;
- throughput и packet loss;
- поведение разных mobile/router firmware;
- сети с меньшим фактическим path MTU.

Для этих проверок подготовлена отдельная [ручная матрица](../manual-checks/awg31-warp-interoperability.md). Успешный импорт или один начальный handshake не считается полным interoperability test.

## Частые вопросы

### Cloudflare начал поддерживать AWG 3.1?

Нет. Cloudflare остаётся обычным WireGuard peer. Генератор использует только те AWG-механизмы, которые либо локальны, либо оставляют пакет допустимым stock WireGuard input.

### Почему content padding разрешён, если Cloudflare не знает диапазон?

Потому что диапазон используется отправителем до шифрования. После расшифрования реальная длина IP-пакета берётся из стандартного IP-заголовка.

### Должен ли `ContentPaddingAddition` совпадать на обеих сторонах?

Нет. Принимающая сторона не использует этот диапазон для расшифрования или handshake.

### Почему `RandomTrailers` нельзя разрешить как experimental option?

Потому что он меняет размер handshake datagram и требует специальной receive-side обработки. Это не локальный риск клиента, а несовместимый wire-format для Cloudflare peer.

### Почему `DisableCookies` разрешён?

Он управляет локальной генерацией Cookie Reply и связанной anti-DoS веткой. Формат обычного handshake не меняется.

### Безопаснее ли включить `DisableCookies`?

Нет. Это компромисс fingerprinting/anti-DoS. Для более консервативного поведения передайте `disableCookies=off`.

### Можно ли отключить новый padding default?

Да: `contentPaddingAddition=off`, `0` или `0-0`.

### Почему максимум равен 65535, если Go UAPI использует uint32?

Публичный официальный `.conf` parser и ABI для этих полей используют `u16_range_t`. Генератор валидирует формат, который фактически импортируется конфигурационными инструментами.

### Почему у AWG 3.0 всё ещё нет `vpn://`?

Потому что отдельное достоверное историческое значение `protocol_version` для него не найдено. Генератор не создаёт неподтверждённый импортный контракт.

### Гарантирует ли 2.7.1 работу в любой сети?

Нет. Блокировки UDP, DPI, path MTU, доступность endpoint, версия клиента и особенности прошивки остаются внешними факторами.

## Известные ограничения 2.7.1

- Нет локально выполненного real-device/WARP rekey теста.
- Нет универсального списка минимальных версий всех AWG-клиентов.
- AWG 3.0 остаётся без `vpn://`.
- Header protection и RandomTrailers несовместимы с WARP peer.
- `DisableCookies=on` ослабляет локальную cookie anti-DoS ветку.
- Content padding способен влиять на throughput и фрагментацию в отдельных сетях.
- Обычные WireGuard приложения не являются поддерживаемыми импортёрами AWG 3.x `.conf`.

## Итог

2.7.1 не пытается превратить Cloudflare в AWG peer. Релиз точнее проводит границу между параметрами, которым действительно нужна поддержка удалённой стороны, и параметрами, которые могут безопасно работать локально или внутри стандартного WireGuard transport payload.

Практический результат: AWG 3.0/3.1 профили получают больше штатной обфускации, API становится строже и понятнее, а опасные для WARP wire-format изменения остаются недоступными. При этом документация прямо отделяет доказанное по исходному коду и автоматическим тестам от реальной сетевой совместимости, которую ещё необходимо подтвердить ручной матрицей.
