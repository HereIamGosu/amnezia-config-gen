## Audit of promises nobody waits for

Scope: `api/`, `src/server/`, `server.js`. Looked for: an `async` call without `await`, `return` or `.catch`; `.then(` without a rejection handler; a `new Promise` executor that can throw synchronously; an `async` callback given to `setTimeout`, `setInterval` or `on(…)`; `Promise.all`/`race` without handling; a timer or event callback that can throw outside any handler. Callers of each `async` function were taken from CodeGraph and `rg`.

### Findings

| # | Place | Defect | Reachable | Fix | Test (red before the fix) |
| --- | --- | --- | --- | --- | --- |
| 1 | `api/warp.js` `httpRequestOnce` | The timeout timer was armed before `https.request`. Node refuses a request path or header value synchronously; the executor then rejected (handled, the visitor got 500), but the timer stayed armed and, 20 s later, its callback read `req` in its temporal dead zone. The `ReferenceError` was thrown outside any handler and would end the process. | Yes: the path carries the registration `id` (`reg/${id}`) and the `Authorization` header the `token`, both from the Cloudflare answer. | 2 | `src/server/ipListFetch.js` `httpsJsonOnce`, `fetchAntifilterOnce`; `src/server/communityIpFetch.js` `fetchListOnce` | Same order as finding 1. | Not today: the opencck path comes from `URLSearchParams`, the community list name from a whitelist, the antifilter path is a constant; the headers are constants. | Same fix (`ipListFetch.js:50`, `:204`; `communityIpFetch.js:87`). | "opencck, community list and antifilter refused → empty result, and no timer fires later" |

### Global handler

No `process.on('unhandledRejection')` was added (owner decision No. 12, 2026-10-31): a handler that logs and carries on would hide defects of this kind; a crash is visible as a container restart, and the blue/green controller keeps the previous slot.

### Observation outside the audit class

A POST to `/api/warp` with `Content-Type: application/json` and an empty body gets no answer until the 60 s deadline (504): `server.js:187` has already read the stream, `req.body` stays unset, and `readRequestJson` waits for an `end` event that has passed. Checked on 2026-10-31 against `server.js` with the network cut off (no answer within 5 s; `{}` and an empty `text/plain` body answered at once). Nothing is thrown and nothing crashes; fixing it changes the answer to a malformed request, so it is left for a later release.
