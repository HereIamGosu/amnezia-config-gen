# AmneziaWG Config Generator 2.7.2

## CPS correctness: безопасный Auto и проверяемые I1-профили

Дата выпуска: 19 сентября 2026 года.

Версия 2.7.2 исправляет Issue #5 — ситуацию, в которой часть предлагаемых генератором CPS/I1-профилей могла не устанавливать соединение с Cloudflare WARP либо показывать handshake без работающего интернет-трафика.

Главное изменение релиза — новая политика доверия к CPS. Рекомендуемый режим `Auto` больше не выбирает протокол только потому, что генератор умеет собрать похожую последовательность байтов. В автоматический пул входят исключительно профили с имеющимся положительным опытом использования в WARP и отдельными структурными тестами. Непроверенные варианты остаются доступны только как явный эксперимент, а неподдерживаемый TLS удалён из интерфейса и отклоняется API.

В результате:

- `Auto` выбирает только `Static`, `SIP` или `STUN`;
- `QUIC`, `DNS` и `DTLS` доступны явно со статусом `experimental`;
- `TLS` имеет статус `unsupported` и больше не представлен как нормальный CPS для WARP;
- неизвестное значение `cps` возвращает HTTP 400 вместо скрытого перехода в Auto;
- QUIC больше не является открытым псевдо-Initial: реализованы Initial key derivation, AEAD packet protection и header protection по RFC 9001;
- QUIC-пакет сохраняется целиком и имеет размер 1200 байт — прежнего обрезания до 1000 байт нет;
- DNS перестроен из query-shaped варианта в согласованный response-shaped packet;
- API и интерфейс показывают, какой протокол был запрошен и какой фактически выбрал Auto;
- телеметрия получает только категориальные CPS-метаданные и никогда не получает содержимое `I1`.

Это patch-релиз с изменением поведения CPS по умолчанию. Форматы `.conf` и `vpn://`, endpoint intelligence, маршрутизация и WARP-регистрация не менялись.

---

## Коротко: что изменится для пользователя

### Если выбран Auto

До 2.7.2 режим Auto мог случайно выбрать QUIC, DNS или DTLS, хотя их реальная совместимость с WARP не была подтверждена. Пользователь видел только `Auto` и не знал, какой именно `I1` попал в конфигурацию.

В 2.7.2 Auto использует только стабильный пул:

```text
Static
SIP
STUN
```

После генерации результат показывает фактический выбор, например:

```text
Auto → SIP
```

При `count=1..3` каждый конфиг разрешает Auto независимо. Поэтому варианты одного ответа могут получить разные стабильные CPS-профили. Метаданные возвращаются отдельно для каждого элемента `configs[]`.

### Если протокол выбран явно

Явно выбранный протокол больше не заменяется другим без уведомления:

```text
cps=stun    → STUN
cps=sip     → SIP
cps=static  → Static
cps=quic    → QUIC (experimental)
cps=dns     → DNS (experimental)
cps=dtls    → DTLS (experimental)
cps=tls     → HTTP 400, unsupported_cps_protocol
cps=garbage → HTTP 400, invalid_cps_protocol
```

Только Auto вправе попробовать другой стабильный генератор, если выбранный кандидат неожиданно завершился ошибкой. Повтор ограничен числом элементов стабильного пула и не раскрывает raw CPS в логах.

## Почему понадобился релиз 2.7.2

Автор Issue #5 проверил CPS на конфигурации AWG 2.0 и сообщил следующую картину:

| Протокол | Наблюдение пользователя |
|---|---|
| QUIC | не работает |
| DNS | не работает |
| TLS | не работает |
| STUN | работает |
| SIP | работает |
| Static | работает |

Сбой проявлялся двумя способами: соединение либо не устанавливалось, либо выглядело установленным, но интернет-трафик не проходил. Смена WARP-порта и endpoint не исправляла ситуацию.

Этот отчёт является важным interoperability evidence, но не заменяет спецификацию протоколов. Поэтому исправление началось с полного аудита CPS-пути: истории проекта, формата AWG I-полей, текущих генераторов, RFC 9000/9001 и закреплённых upstream-ревизий.

Аудит выявил три независимые проблемы.

### 1. QUIC был только внешне похож на Initial

Старый генератор создавал QUIC v1 Long Header и вкладывал TLS ClientHello в CRYPTO frame, но оставлял payload открытым. Он не выводил Initial secrets, не выполнял AEAD-шифрование и не применял Header Protection.

Такой пакет нельзя было корректно называть защищённым QUIC Initial по RFC 9001. Простого узнаваемого заголовка недостаточно, если сетевое оборудование проверяет более глубокую структуру трафика.

### 2. Auto включал неподтверждённые режимы

В автоматическом пуле находились QUIC, DNS и DTLS. Это превращало рекомендуемую настройку в случайный выбор между проверенными и экспериментальными вариантами. Даже корректная будущая реализация QUIC не устранила бы эту продуктовую ошибку: unit-тест протокольной структуры не доказывает работу через конкретную сеть и WARP peer.

### 3. В API существовал скрытый fallback

Неизвестное значение CPS могло незаметно превратиться в Auto. Пользователь или интеграция запрашивали один режим, а получали другой, не имея точного объяснения в ответе API.

Отдельно был подтверждён прежний вывод о TLS: обычная TLS record layer рассчитана на TCP и является аномальной формой для этого UDP-пути. Подмена TLS на DTLS также была бы скрытым изменением семантики, поэтому TLS получил явный статус `unsupported`.

## Политика протоколов в 2.7.2

| Протокол | Статус | Доступен в Auto | Основание решения |
|---|---|---:|---|
| Static | stable | да | существующий проверенный пул WARP CPS проекта |
| SIP | stable | да | положительный пользовательский и проектный опыт, структурные тесты |
| STUN | stable | да | положительный отчёт Issue #5, проверка структуры и FINGERPRINT |
| QUIC | experimental | нет | RFC 9001 primitives и packet round-trip проверены; live WARP interop не выполнен |
| DNS | experimental | нет | перестроен в согласованную response-shaped форму; live WARP interop не выполнен |
| DTLS | experimental | нет | проверяется структура record/handshake; live WARP interop не выполнен |
| TLS | unsupported | нет | TLS-over-UDP не поддерживается в этом WARP CPS-потоке |

Статус `experimental` означает, что генератор строит внутренне согласованную форму и проверяет её автоматически, но не обещает успешный handshake, DNS и передачу данных в реальной сети.

Повышение протокола до stable требует воспроизводимого результата как минимум на двух клиентских платформах и двух независимых сетях. Один импорт конфига или один handshake без рабочего трафика недостаточен.

## Новая реализация QUIC

### Что реализовано

Генератор использует встроенный `node:crypto` и строит защищённый QUIC v1 Initial-shaped packet:

1. Создаёт случайные DCID и SCID.
2. Формирует минимальный TLS 1.3 ClientHello с внутренним безопасным пулом SNI, supported versions, groups, signature algorithms, key share и QUIC transport parameters.
3. Помещает ClientHello в QUIC CRYPTO frame.
4. Выводит Initial secret из DCID и QUIC v1 initial salt.
5. Получает client initial secret, `quic key`, `quic iv` и `quic hp` через HKDF labels.
6. Шифрует payload с AES-128-GCM.
7. Применяет AES-based QUIC Header Protection.
8. Добавляет PADDING frames так, чтобы итоговый UDP datagram занимал ровно 1200 байт.

Криптографические derivation проверяются известными векторами RFC 9001 Appendix A. Тест также снимает header protection, восстанавливает packet number, расшифровывает payload и извлекает исходный CRYPTO frame.

### QUIC varints

Кодирование и декодирование QUIC variable-length integers использует `BigInt` и проверяется на границах:

```text
63 / 64
16383 / 16384
2^30 - 1 / 2^30
```

Это устраняет риск signed truncation в 8-byte представлении.

### Почему пакет больше не обрезается

Раньше общий ограничитель мог взять структурированный пакет и механически оставить только первые 1000 байт. Для зашифрованного QUIC это разрушает ciphertext и authentication tag.

В 2.7.2 готовый 1200-byte packet делится на соседние fixed-byte операции CPS DSL:

```text
1000 bytes + 200 bytes
```

Все байты сохраняются в исходном порядке. Генератор не создаёт oversized ciphertext с последующим `slice()`.

### Что не утверждается

Релиз не называет результат полноценным браузерным QUIC-соединением и не обещает прохождение любого DPI. CPS отправляет сформированную последовательность перед WireGuard handshake; сервер генератора не устанавливает QUIC-сессию и не посылает тестовые UDP-пакеты.

Поэтому QUIC остаётся `experimental` до отдельной live interoperability проверки.

## Новая реализация DNS

Старый DNS-вариант формировал query-shaped packet. Аудит актуального клиента Amnezia показал более подходящий precedent для SpecialJunk1 — response-shaped DNS payload.

В 2.7.2 шаблон содержит:

- `<r 2>` для runtime Transaction ID;
- flags `0x8180`: response, recursion desired/available, `RCODE=0`;
- один question;
- один A answer;
- compression pointer `0xc00c` на имя вопроса;
- TTL 300;
- согласованные длины и счётчики секций.

Структурный тест разворачивает CPS-шаблон, подставляет Transaction ID и разбирает результат как DNS-пакет. Live-совместимость с WARP пока не подтверждена, поэтому DNS доступен только явно и отмечен `experimental`.

---

## STUN, SIP и Static

Стабильный Auto-пул также получил отдельное регрессионное покрытие.

### STUN

Сохранена существующая вариативность username, software и padding. Тест проверяет message type, declared message length, magic cookie, структуру attributes и корректный `FINGERPRINT`.

### SIP

Генератор продолжает использовать согласованную пару SIP request/response-shaped payloads. Тесты проверяют CPS-синтаксис и разворачивание в непустую последовательность байтов.

### Static

Сохраняется существующий пул заранее подготовленных WARP CPS-шаблонов. Каждый элемент проходит общий путь генерации без скрытого fallback.

---

## TLS и DTLS

### TLS

TLS удалён из селектора интерфейса. Запрос `cps=tls` не заменяется DTLS или Auto, а возвращает контролируемую ошибку:

```json
{
  "success": false,
  "error": "unsupported_cps_protocol",
  "allowedCpsProtocols": [
    "auto",
    "static",
    "sip",
    "stun",
    "quic",
    "dns",
    "dtls"
  ]
}
```

### DTLS

DTLS остаётся отдельным протоколом, а не неявной заменой TLS. Генератор формирует согласованный DTLS record/ClientHello envelope, который проверяется структурным тестом. Реальная совместимость с WARP не подтверждена, поэтому режим имеет статус `experimental` и не входит в Auto.

## API и диагностика

Ответ `/api/warp` теперь содержит безопасные CPS-метаданные:

```json
{
  "cpsRequested": "auto",
  "cpsResolved": "stun",
  "cpsStability": "stable",
  "configs": [
    {
      "cpsRequested": "auto",
      "cpsResolved": "stun",
      "cpsStability": "stable"
    }
  ]
}
```

Top-level поля повторяют первый конфиг для простых клиентов. При генерации нескольких вариантов точным источником являются поля каждого элемента `configs[]`.

Для пользовательского `i1` или `i1Ref` metadata показывает `custom`, не пытаясь угадать протокол по содержимому. Если I1 отсутствует, возвращается `none`.

Ошибки валидации возникают до регистрации WARP. Неверный CPS не расходует внешний запрос и не маскируется случайно выбранным Auto-профилем.

## Изменения интерфейса

Селектор CPS синхронизирован с серверным registry:

- Auto явно описан как stable-only;
- QUIC, DNS и DTLS имеют заметку `experimental`;
- TLS удалён;
- подписи больше не обещают неподтверждённую совместимость;
- результат показывает разрешение Auto или experimental-статус явного режима.

При проблемах с экспериментальным профилем интерфейс рекомендует сначала сравнить поведение с Auto, Static, STUN или SIP. Это диагностический baseline, а не обещание работы в любой сети.

---

## Privacy-safe телеметрия

В allowlist добавлены только три категориальных поля:

```text
cps_requested
cps_resolved
cps_stability
```

В телеметрию не передаются содержимое `I1`, raw packet, `.conf`, `vpn://`, private key, WARP token, пользовательские IP, account data и внутренний SNI.

Регрессионный тест специально передаёт поле `i1` в sanitizer и проверяет, что оно отбрасывается.

## Совместимость и сохранённые инварианты

Исправление ограничено CPS/I1-подсистемой. Сохранены:

- uppercase `I1`;
- порядок `I1-I5` при `cps5=1`;
- WARP `S1-S4 = 0`;
- WARP `H1-H4 = 1,2,3,4`;
- `MTU = 1280`;
- Legacy, AWG 2.0, AWG 3.0 и AWG 3.1 пути;
- mobile/router composition;
- IPv4/IPv6 варианты;
- `.conf` и `vpn://` contracts;
- endpoint cache, endpoint health и port selection;
- Cloudflare registration;
- CIDR sources и route presets;
- request-size limits и rate limiting.

Сервер по-прежнему только строит конфигурацию. Он не стал QUIC scanner, STUN client или UDP probe и не отправляет сгенерированные CPS-пакеты в сеть.

## Что автоматические тесты не доказывают

Автотесты подтверждают структуру пакетов, криптографическую внутреннюю согласованность, API-контракт, безопасность Auto и сохранение конфигурационных инвариантов. Они не доказывают прохождение конкретного DPI и не заменяют реальный WARP-сеанс.

На момент подготовки релиза локально не выполнены импорт каждого CPS в актуальные AWG-клиенты, handshake для QUIC/DNS/DTLS, DNS lookup, HTTPS browsing, large TCP transfer, UDP traffic, reconnect, rekey и сравнение независимых сетей.

Для фиксации результатов подготовлена [ручная CPS interoperability matrix](../manual-checks/cps-interop.md). Документ запрещает сохранять private keys, raw I1 и полный конфиг.

## Диагностика

### Auto выбрал неожиданный профиль

Проверьте `cpsResolved` в ответе или строку `Auto → …` в карточке результата. При `count>1` смотрите metadata конкретного конфига: варианты выбираются независимо.

### Экспериментальный CPS не устанавливает соединение

Сначала сгенерируйте конфиг с Auto, Static, STUN или SIP на том же endpoint и порте. Если стабильный baseline работает, зафиксируйте клиент, ОС, сеть, CPS, порт и категориальный результат в manual matrix. Не публикуйте полный конфиг.

### Handshake есть, но интернет не работает

Проверяйте не только `latest handshake`. Отдельно выполните DNS lookup, откройте HTTPS-страницу, проверьте передачу данных и reconnect. Именно такой частичный сбой был описан в Issue #5.

### API отвечает `unsupported_cps_protocol`

Такой ответ ожидается для `cps=tls`. Используйте Auto или явно один из поддерживаемых ID. Сервер намеренно не подменяет TLS на DTLS.

### API отвечает `invalid_cps_protocol`

Проверьте регистр и spelling значения. Допустимы `auto`, `static`, `sip`, `stun`, `quic`, `dns` и `dtls`.

## Частые вопросы

### QUIC теперь полностью совместим с любым DPI?

Нет. Реализованные RFC 9001 primitives и packet round-trip проверены автоматически, но поведение middlebox и WARP в конкретной сети подтверждается только live-тестом.

### Почему QUIC не добавлен в Auto после реализации шифрования?

Потому что протокольная корректность и реальная interoperability — разные уровни доказательств. Auto предназначен для рекомендуемого безопасного выбора, а не для экспериментов.

### Почему DNS остаётся experimental?

Новая response-shaped структура лучше обоснована и тестируется, но ещё не прошла воспроизводимую проверку на нескольких клиентах и сетях.

### Почему STUN считается stable?

Для него есть положительный пользовательский отчёт из Issue #5, существующий проектный путь и автоматическая проверка структуры, включая FINGERPRINT.

### Почему TLS удалён, а DTLS оставлен?

TLS record over UDP аномален для этого пути. DTLS предназначен для datagram transport, но пока остаётся экспериментальным из-за отсутствия live WARP evidence.

### Может ли явный QUIC незаметно превратиться в Static?

Нет. Явные режимы либо генерируются как запрошено, либо возвращают ошибку. Перебор альтернатив разрешён только внутри Auto и только среди стабильных кандидатов.

### Отправляет ли сервер тестовые пакеты в интернет?

Нет. Генератор создаёт CPS DSL внутри конфигурации. Реальная отправка происходит только на клиентском устройстве после импорта конфига.

### Нужно ли менять уже работающий Static/SIP/STUN конфиг?

Нет. Релиз не требует миграции существующего рабочего конфига. Новая политика влияет прежде всего на последующие генерации через Auto и на диагностику явных режимов.

---

## Известные ограничения 2.7.2

- QUIC, DNS и DTLS не прошли локальную live-проверку с WARP и остаются experimental.
- Статус stable отражает имеющиеся проектные и пользовательские данные, а не гарантию работы в любой сети.
- Результат зависит от клиента, версии AWG, сети, UDP-фильтрации и поведения DPI.
- Сервер не может автоматически проверить CPS до выдачи конфига, поскольку не отправляет пользовательский трафик.
- Несколько конфигов с Auto могут получить разные стабильные CPS-профили; необходимо смотреть per-config metadata.
- Полный repository-wide lint остаётся загрязнён существующим вложенным worktree, не входящим в релиз.

## Итог

Версия 2.7.2 меняет базовый принцип CPS-генерации: количество доступных кнопок больше не важнее предсказуемости подключения.

Auto теперь ограничен стабильными Static, SIP и STUN. QUIC получил реальную Initial packet protection вместо открытого протокольного макета, DNS — согласованную response-shaped структуру, а DTLS — явный экспериментальный статус. TLS и неизвестные режимы больше не маскируются fallback-поведением. Пользователь и интеграция видят фактически выбранный протокол, не раскрывая raw I1 в API-диагностике или телеметрии.

Релиз не обещает универсального обхода DPI. Он делает более важную вещь: генератор перестаёт рекомендовать и случайно выбирать варианты, для которых нет достаточных доказательств работоспособности, а каждый экспериментальный протокол получает проверяемую техническую основу и честно обозначенную границу уверенности.
