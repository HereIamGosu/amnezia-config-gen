# AmneziaWG Config Generator 3.1.8

## WARP registration: IPv4-only instead of 500, fixed answers to Cloudflare failures, outcome counters

Prepared on 2026-11-01 after 3.1.7 (`85a4eba`). Successful generation does not change: for an answer of Cloudflare with an IPv6 address the `.conf`, `vpn://` and the response fields are those of 3.1.7.

## What changed for users

**No IPv6 in the registration.** When Cloudflare registered the device without a usable IPv6 address (absent, empty or not an address), the visitor got HTTP 500 «Cloudflare вернул некорректный IPv6 адрес». Now the config is built as with `ipv6=0`: `Address` holds only the IPv4 address, `AllowedIPs` has no `::/0` and no IPv6 routes of presets, also when `ipv6=1` was asked, so that IPv6 traffic is not routed into a tunnel whose interface has no IPv6 address. The answer is 200 with one line in `warning`:

```text
WARP registration returned no IPv6 address for config(s) 2: the config is IPv4-only.
```

The page shows it in its language. With `count` > 1 only the configs without IPv6 are IPv4-only, and the line names them. With `mobile=1` the config is IPv4-only anyway (invariant I7), so no line is added. An unusable IPv4 address is still a failure (502, below). Whether Cloudflare has ever answered `/api/warp` without IPv6 is not known; the new counters (below) will show it.

**Cloudflare failures.** The visitor sees a fixed text per kind of failure instead of Cloudflare's own text or «Ошибка с кодом N».

## The API: answers to a failed registration

Each request to Cloudflare (`POST reg`, `PATCH reg/{id}`) maps to a class, the class to an answer. The body is `{ success: false, message }` with a fixed Russian `message`; there is no `error` field. `GET reg/{id}` after `PATCH` still falls back to the `POST` config on any failure.

| Cloudflare outcome | 3.1.7 | 3.1.8 | `Retry-After` |
| --- | --- | --- | --- |
| 2xx, body not JSON | 500 | 502 | — |
| 2xx, empty body, `null`, no string `id`/`token`, no peers, unusable IPv4 | 500 | 502 | — |
| 2xx with an `id` or `token` Node cannot put into the next request | 500 | 502 | — |
| answer over 2 MB | 500 | 502 | — |
| 3xx | 500 | 502 | — |
| 400 | 400, `error` and `message` = Cloudflare's text | 502, no `error` | — |
| 401, 403, 404, 405, 409 and other 4xx except 408 and 429 | the same code, Cloudflare's text | 502 | — |
| 408 | 408 | 503 | `60` |
| 429 after three attempts | 429, Cloudflare's text, no header | 429 | Cloudflare's value if an integer 1–3600, otherwise `60` |
| 501 | 501 | 502 | — |
| 500, 502, 503, 504 and other 5xx | the same code | 503 | `60` |
| network failure, timeout (20 s) | 500 «Ошибка запроса: …» / «Таймаут запроса к Cloudflare API.» | 503 | `60` |
| 2xx without a usable IPv6 address | 500 | 200, IPv4-only config, `warning` | — |

Texts: 429 — «Cloudflare временно ограничил создание устройств WARP. Повторите через минуту; если ошибка держится, это сбой на стороне Cloudflare, а не вашего подключения.»; 503 — «Сервис регистрации Cloudflare WARP сейчас не отвечает. Повторите позже.»; 502 — «Cloudflare не принял запрос регистрации WARP. Это сбой на стороне сервиса, а не ваших настроек.» On `/en` they stay Russian: without an `error` code the page cannot tell them from the other 502 (empty route list) and 429 (own rate limit) answers. Codes `warp_registration_*` and a localised text are planned for a minor release.

The retries are those of 3.1.7: network errors `ECONNRESET`, `ETIMEDOUT`, `ENOTFOUND`, `EAI_AGAIN`, `ECONNREFUSED`, `EPIPE`, «socket hang up», the timeout and the codes 429 / 502 / 503 / 504, three attempts in all. A 500, 501, 408, another network code (`EHOSTUNREACH`) or an answer over 2 MB, whatever its code, is one attempt.

Unchanged: successful answers; the own rate limit (429 with `Retry-After`, «Слишком много запросов. Попробуйте позже.»); the refusals before registration (`cps_chain_invalid`, `cps_chain_gap`, unknown presets, `warpPort`, Lab Auto `lab_*`); 502 when every route list source failed after registration; 500 for an exception without a status.

**For an API client** this changes the code and body of failed requests only. A client that branches on 403, 500 or on Cloudflare's text in `message`, or reads `error` of a 400 from Cloudflare, sees 502/503 and the fixed text instead. A client that reads only `success` and `message` keeps working.

**`POST` with an empty JSON body.** `Content-Type: application/json` with an empty body used to wait for the 60 s deadline (504) on the self-hosted server; it is now `{}`, as an empty body of another type already was.

## Evidence boundary

- All Cloudflare outcomes were reproduced with a fake `https.request` (no network): each row of the table in `__tests__/warp-registration-errors.test.js`, with the number of requests made; the IPv4-only path in `__tests__/warp-ipv4-degradation.test.js`, compared field by field with the config from an answer with IPv6 in all four modes, with `ipv6=1`, split routes, `count=3`, `mobile=1`, `vpn://` and Lab Auto.
- The requests to Cloudflare are compared with 3.1.7 byte for byte (method, host, port, path, agent, headers in order, body) in `__tests__/warp-registration-request.test.js`. Generation was compared with `v3.1.7` on the local oracle stand (68 parameter sets × 8 runs, `.conf` structure and fixed fields): no set differs; 1000 router configs stayed within the router bounds.
- No WARP registration was made for this release; no real Cloudflare answer without IPv6 or with these failures was observed. No client was tried with an IPv4-only config from this path.

## For developers

- `src/server/warpRegistration.js` (new): request headers, `httpRequestOnce` (its timer is still armed after `https.request`, the 3.1.7 order), retries, `registerDevice(publicKey)`, the failure classes (`registrationError`: `source`, `registrationClass`, `upstreamStatus`, `retryAfterS`), `refusalFor`, the counters and `flushRegistrationStats`. `isValidIPv4`/`isValidIPv6` moved there and are still in `api/warp.js` `__internals`.
- `api/warp.js`: the handler's `catch` checks `labCode`, then `registrationClass`, then the old `statusCode` logic. `generateWarpConfig` gives the `ipv6=0` config when the registration has no IPv6 address (`meta.ipv6Missing`, not in the response).
- `server.js`: an empty JSON body becomes `req.body = {}`; `shutdown` writes the counter line.
- Frontend: `warp_ipv4_only` in `KNOWN_API_WARNINGS` (`result-explanation.js`), `warningText` (`result.js`), locale key `risk_warp_ipv4_only`.
- Tests: new `warp-registration-request`, `warp-ipv4-degradation`, `warp-registration-errors`, `warp-registration-stats`; `__tests__/helpers/warp-harness.js` takes a Cloudflare answer (status, body, headers, network failure, no answer); `__tests__/helpers/free-port.js`; additions to `invariant-i6-ipv4-default`, `secret-leakage`, `result-explanation`, `e2e/generate`. Expected codes changed in `unhandled-rejection-audit.test.js` (refused connection and timeout 500 → 503, non-JSON 2xx and a refused `id`/`token` 500 → 502, split with a Cloudflare 403 403 → 502, offline `server.js` `/api/warp` and split 500 → 503) and in `error-classes.test.js` (a request error 500 → 503); the assertions about unhandled rejections and timers are unchanged.

## For the operator

A push to `main` deploys it. No host, controller, nginx or Endpoint Lab change. After the deploy the active slot's log gets a line per 10 minutes with registrations:

```text
[warp-registration-stats] window=600s profile=legacy ok=12 ok_ipv4_only=0 rate_limited=0 unavailable=0 rejected=0 malformed=0
```

No line in a quiet window is not a failure. `ok_ipv4_only` above zero means Cloudflare registered devices without IPv6; `rate_limited`, `unavailable`, `rejected` or `malformed` above zero is the first recorded registration failure. Reading the line daily belongs to the `tg-ops` report (a separate task). Smoke: `X-App-Revision`, `/`, `/en`, `/lab` with assets `?v=3.1.8`, `/api/healthcheck`, `/api/status` 200. Rollback: `amnezia-deploy rollback`; the counters live in process memory only.
