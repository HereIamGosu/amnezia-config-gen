# Release 3.1.9 — Source Audit

Checked on 2026-11-01 from `5ac5e26` (3.1.8 plus its ledger commit). No upstream source was read: the release changes which IPv4 routes a split config gets and when they are resolved; the WireGuard/AmneziaWG wire format, AWG profiles, CPS, the `vpn://` schema and Endpoint Lab are untouched. The protocol evidence of [3.1.0](3.1.0-source-audit.md) is unchanged; `npm run evidence:check` is part of the release checks.

## Protocol surface

Without presets, or with `routeMode=full`, nothing changes: checked against `v3.1.8` on the local oracle stand (real handler, fake Cloudflare registration, the 68 parameter sets of 3.1.7, 8 runs each, `.conf` structure and fixed fields): no set differs, and 1000 router configs stay within `Jc ≤ 2`, `40 ≤ Jmin ≤ 64`, `Jmin + 64 ≤ Jmax ≤ 128`.

With presets only the `AllowedIPs` line changes. Checked against `v3.1.8` on a split stand (both handlers under one fake network; the opencck answers are the public lists recorded on 2026-11-01; 48 sets in four modes with `count=3`, `mobile=1`, `ipv6=1`, `router=1` and Lab Auto): every other line, the response fields and `warning` are equal (keys, junk sizes and CPS bytes compared by shape); the IPv4 part of `AllowedIPs` covers exactly the addresses of 3.1.8 minus `162.159.192.0/24`, `162.159.193.0/24`, `162.159.195.0/24`, `162.159.204.0/24`; the IPv6 part is equal line by line; `vpn://` carries the same `.conf` and `allowed_ips`.

Invariants on the new path, each with a test through the handler (`__tests__/route-aggregation-api.test.js` unless named): I6 — a split config without `ipv6=1` has no IPv6 route; I7 — `mobile=1` with `ipv6=1` has none either (also `warp-route-preresolve.test.js`: the lists are asked for IPv4 only); I8 — `mobile=1&router=1` keeps `Jc = 2`, `Jmin = 64`, `Jmax = 128` in all four modes and every config of `count=3`; I10 — `allowed_ips` of `vpn://` equals `AllowedIPs`; I11 — Lab Auto and hostname give the same `AllowedIPs`, only `Peer.Endpoint` differs; the 3.1.8 degradation — a registration without IPv6 drops the IPv6 routes of its own config only, the shared list keeps them for the others. New I14: the IPv4 part of a split `AllowedIPs` covers exactly `S \ E_fixed` (`S` the union of the presets' routes) in no more blocks than that set needs (`__tests__/invariant-i14-route-aggregation.test.js`). No invariant is weakened.

## Aggregation

`aggregateCidrs` reads a well-formed IPv4 CIDR (octets 0–255 and prefix 0–32 without leading zeros) as the interval of its network, host bits dropped; sorts, merges overlapping, nested and adjacent intervals in one pass, subtracts the excluded intervals and splits each remaining interval greedily into the largest aligned blocks (`ctz(0)` = 32). IPv6 entries (with `:`) and malformed IPv4 entries (a bare address, `/33`, leading zeros) pass unchanged. The result is sorted with the default string sort of earlier versions. The oracle in `__tests__/helpers/cidr-coverage.js` shares no code with the module: membership changes only at a block's start and right after its end, so comparing those points decides set equality; the minimum number of blocks is counted on a painted /16 by a prefix tree.

Checked by mutation (`release-gates-3.1.9/mutation-gate.js`), each mutant fails its tests: merging an unaligned pair of `/32`, merging across a gap, adjacency without `+ 1`, `ctz(0)` = 31, aggregating IPv6, dropping malformed IPv4, a numeric sort, the cut skipped, one subnet missing from the cut, the cut applied to the full tunnel, the cut only in one endpoint mode.

## Resolution before registration

The handler resolves the routes after the Lab Auto selection and before the first registration, and passes them to every config of the request. The Lab selection reads the pool file and picks endpoints; it records nothing, so a 502 after it has nothing to undo (`endpointProvider.js` `selectForGeneration`; the shadow counters run only in hostname mode and only after a response). A 502 by routes is not a registration outcome: `[warp-registration-stats]` does not count it (`warp-route-preresolve.test.js`). The IPv4-only filter of a registration without IPv6 stays in `generateWarpConfig`, after each registration. `generateWarpConfig` called without resolved routes keeps the concurrent lookup with its `.catch` (3.1.7 audit).

Price: the lookup no longer overlaps the registration. With a warm cache (10 minutes, the page's preview fills it for the same key) this costs nothing; with a cold one the generation waits for opencck first. Not measured.

## Route budget

`ROUTE_LIMIT = 1000` and `classifyBudget` in `src/server/routeBudget.js`: `over` above the limit, `warn` from 800 up to the limit itself. The server adds `Route budget: …` to `warning` when the list after the cut and the merge is over; it never refuses. The page still counts the raw `count4` of `/api/iplist` against its own `MAX_CIDR_LIMIT = 1000`. Since the cut can add up to nine lines per list holding `162.158.0.0/15`, the server number can now exceed the page number: a set the counter shows just under 1000 can get the warning. The merge works the other way, so a set the counter shows over 1000 can stay under it on the server. Both numbers in one place come with the minor part of the route budget work.

## Measurement

The public lists of the 49 presets were read once on 2026-11-01 through `fetchCidrsForDomains` (opencck, itdoginfo, antifilter; from a workstation behind its VPN, not from the server), without `/api/warp` and without registrations. The numbers in the release notes are recomputed from the saved lists by a separate check. 24 presets got the same 71 routes of the antifilter fallback that day; why opencck gave them nothing from the workstation is not known, and their own lists (and whether any of them covers the endpoint subnets) were not measured. The release notes speak of the other 25. The three largest lists (YouTube, TikTok, WhatsApp) are fixtures of `cidr-aggregate.test.js`.
