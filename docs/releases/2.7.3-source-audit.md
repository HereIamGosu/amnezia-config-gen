### `.conf` range width versus Go UAPI

The [Go UAPI](https://github.com/amnezia-vpn/amneziawg-go/blob/b5928efb6ca19f0153958460c3d141f04abc5c2e/device/uapi.go#L481-L489) parses `ContentPaddingAddition` as `UintRange`; the official [tools `.conf` parser](https://github.com/amnezia-vpn/amneziawg-tools/blob/ee0f0a9aa34ff0a0da4b3433b9512781cfe02843/src/config.c#L552-L601) uses `u16_range_from_string` for CPA, the five timing fields, and peer `PersistentKeepalive`. The public generator contract is `0..65535`.

There is also an upstream parser caveat: the current [`u16_range_from_string`](https://github.com/amnezia-vpn/amneziawg-tools/blob/ee0f0a9aa34ff0a0da4b3433b9512781cfe02843/src/type.c#L40-L69) checks parsed values against `UINT32_MAX` before storing through `u16_range_init`. Values above `65535` can therefore be accepted and narrowed, rather than rejected. Generator validation must reject them itself; it must not rely on upstream parser enforcement. This is an implementation observation, not supported syntax.

### Correction to the 2.7.1 RandomTrailers audit

The historical [2.7.1 audit](2.7.1-source-audit.md) suggested an initial trailer could be zero because the peer UDP window had not been learned. At this pinned revision [`NewPeer` initializes `peer.udpWindow` to `DefaultUdpWindow`](https://github.com/amnezia-vpn/amneziawg-go/blob/b5928efb6ca19f0153958460c3d141f04abc5c2e/device/peer.go#L53-L85) immediately. An empty/unlearned initial window is thus **not** a supported explanation. Random selection or packet-size constraints can still produce zero. This addendum preserves the older audit as a historical snapshot.

### Conflicting community evidence

The [2026-09-19 Issue #4 comment](https://github.com/HereIamGosu/amnezia-config-gen/issues/4#issuecomment-5742526540) reports WARP working with trailers but Proton failing. This is a **community report**, not a primary peer contract or reproducible first-party interoperability record. It warrants manual follow-up, but cannot establish Cloudflare's tolerance of oversized handshake datagrams across versions, networks and rekeys. The conservative WARP block remains. The [manual evidence form](../manual-checks/protocol-evidence.md) defines what a live check must record before promotion.

## Evidence boundary and process

No first-party live evidence was recorded here for WARP handshake, DNS, traffic, reconnect, rekey, long-running stability or performance per capability. Source-confirmed does not mean verified. CPS payload evidence is tracked separately from the source-confirmed `I1`–`I5` mechanism. Current protocol documentation is generated/checked from code through `npm run evidence:generate` and `npm run evidence:check`; this Markdown audit is not a second protocol registry.
