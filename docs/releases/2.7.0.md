# AmneziaWG Config Generator 2.7.0

## AmneziaWG 3.0 и 3.1 для Cloudflare WARP — подробно, доступно и без скрытых обещаний

Release 2.7.0 добавляет два режима: **AmneziaWG 3.0** и **AmneziaWG 3.1**. Генератор использует только те возможности AWG 3.x, которые выполняются клиентом и не требуют изменить сервер Cloudflare.

Главное ограничение релиза:

> Cloudflare WARP остаётся обычным WireGuard peer. Генератор не превращает Cloudflare в AWG 3.x-сервер и не включает функции, для которых обе стороны должны быть настроены как AmneziaWG.

Иными словами, это **WARP-safe клиентский профиль AWG 3.x**, а не полный AWG-транспорт между двумя управляемыми AWG-узлами.

Документ описывает реализацию 2.7.0 и проверенное состояние совместимости на 12 сентября 2026 года. Версии сторонних клиентов и прошивок меняются; точную поддержку всегда нужно сверять для конкретной версии.

---

## Что получает пользователь

- В интерфейсе есть отдельные кнопки AWG 3.0 и AWG 3.1. Все четыре кнопки генерации расположены сеткой 2×2: AWG 1.5 и 2.0 сверху, AWG 3.0 и 3.1 снизу.
- Создаются файлы `AmneziaWarp-AWG3.0.conf` и `AmneziaWarp-AWG3.1.conf`.
- В обоих режимах доступны junk-пакеты, CPS, диапазоны таймеров и диапазон `PersistentKeepalive`.
- AWG 3.1 поддерживает `vpn://` с подтверждённым `protocol_version: "3.1"`.
- AWG 3.0 выдаётся только как `.conf`: историческая версия протокола для `vpn://` не подтверждена первичным источником.
- Опасные для WARP поля нельзя включить через UI, GET, POST, шаблон, mobile- или router-профиль.
- `ContentPaddingAddition` доступен только через API как выключенный по умолчанию эксперимент.
- Legacy и AWG 2.0 сохранены без замены их назначения.

## Как это устроено

```text
AmneziaVPN / AWG 3.x-клиент
        │
        │ junk, CPS, случайные интервалы таймеров
        ▼
стандартный WireGuard wire-format
H1..H4 = 1,2,3,4; S1..S4 = 0
        │ UDP
        ▼
Cloudflare WARP
обычный WireGuard peer, не AWG-сервер
```

Клиент может менять локальное поведение: отправлять junk/CPS-последовательности, варьировать интервалы переподключения и keepalive. Но протокольное сообщение, которое принимает Cloudflare, должно остаться стандартным WireGuard.

Отсюда две группы возможностей:

1. **Клиентские** — не требуют поддержки Cloudflare и разрешены.
2. **Peer-dependent** — меняют wire-format или серверное поведение и поэтому запрещены.

## AWG 3.0 и AWG 3.1: точная разница в генераторе

| Возможность | AWG 3.0 | AWG 3.1 | Причина |
|---|---:|---:|---|
| `.conf` | Да | Да | Основной переносимый формат |
| `Jc/Jmin/Jmax` | Да | Да | Junk создаёт клиент |
| `I1`, опционально `I2..I5` | Да | Да | CPS выполняет клиент |
| Диапазоны таймеров | Да | Да | Значение выбирает клиент |
| Диапазон `PersistentKeepalive` | Да | Да | Keepalive инициирует клиент |
| `ContentPaddingAddition` | Эксперимент | Эксперимент | Совместимость с WARP не доказана достаточно широко |
| `HeaderProtectionKey` | Нет | Нет | Ключ и алгоритм нужны обеим сторонам |
| Ненулевые `S1..S4` | Нет | Нет | Меняют формат WireGuard-сообщений |
| Динамические `H1..H4` | Нет | Нет | Cloudflare ожидает типы `1,2,3,4` |
| `RandomTrailers=on` | Нет | Нет | Требует AWG 3.1 peer |
| `DisableCookies=on` | Нет | Нет | Нельзя менять cookie-поведение неподконтрольного сервера |
| Явные `RandomTrailers=off`, `DisableCookies=off` | Нет | Да | В 3.1 безопасное состояние закреплено в файле |
| `vpn://` | Нет | Да, версия `3.1` | Для 3.0 mapping не подтверждён |

Сетевое поведение профилей намеренно близко. 3.1 отличается явными безопасными флагами и подтверждённым форматом `vpn://`.

## Возможности AWG 3.x простыми словами

### Junk-пакеты

- `Jc` — количество junk-пакетов;
- `Jmin` — минимальный размер в байтах;
- `Jmax` — максимальный размер в байтах.

Для AWG 3.x используется проверенный WARP-safe генератор:

- `Jc`: случайное целое `1..25`;
- `Jmin`: случайное целое `64..800`;
- `Jmax`: не меньше `Jmin + 64` и не больше `1024`.

Значения различаются между конфигурациями. Точное расписание отправки реализует клиент. Больше junk не всегда лучше: растут трафик, нагрузка и расход батареи, поэтому для телефонов и роутеров есть отдельные ограничения.

### CPS — настраиваемые последовательности пакетов

`I1` содержит клиентскую последовательность обфускации. WARP-шаблон подставляет встроенное значение, если не передано собственное `i1` или `i1Ref`.

Опция `cps5=1` добавляет `I2..I5`, только когда существует непустой `I1`. Генератор не создаёт оборванную цепочку без первой последовательности.

CPS не требует изменить Cloudflare, но требует AWG-движок на клиенте. Обычный WireGuard parser может отклонить эти строки или не исполнить их.

### Диапазоны таймеров

AWG 3.x хранит не одно число, а диапазон. Конкретное значение внутри диапазона выбирает клиентская реализация. Генератор сохраняет саму строку, например `100-120`; старый parser, ожидающий одно число, может её не принять.

| Поле | Default | Что регулирует |
|---|---:|---|
| `RekeyAfterTime` | `100-120` | Плановое обновление ключей сессии |
| `RekeyTimeout` | `3-7` | Повтор неудачного рукопожатия |
| `RejectAfterTime` | `150-180` | Момент отказа от устаревшего состояния сессии |
| `KeepaliveTimeout` | `5-15` | Таймер связанной с keepalive активности |
| `MaxHandshakeAttempts` | `15-20` | Допустимое число попыток рукопожатия |
| `PersistentKeepalive` | `25-35` | Фоновый keepalive для сохранения NAT-сопоставления |

Пять первых полей находятся в `[Interface]`, `PersistentKeepalive` — в `[Peer]`.

### Стандартный WireGuard wire-format

- `H1 = 1` — Handshake Initiation;
- `H2 = 2` — Handshake Response;
- `H3 = 3` — Cookie Reply;
- `H4 = 4` — Transport Data;
- `S1 = S2 = S3 = S4 = 0`;
- `HeaderProtectionKey` отсутствует;
- `MTU = 1280`.

Это финальные защитные инварианты. Пользовательские параметры не могут их ослабить.

## Особенности AWG 3.1

AWG 3.1 использует тот же WARP-safe набор junk, CPS и таймеров, но явно содержит:

```ini
RandomTrailers = off
DisableCookies = off
```

`RandomTrailers=on` добавляет случайные хвосты, которые должен понимать peer. `DisableCookies=on` меняет поведение WireGuard Cookie Reply — серверной anti-DoS-защиты. Генератор не управляет Cloudflare, поэтому оба механизма выключены.

Явное `off` делает профиль проверяемым и не оставляет поведение на усмотрение default конкретного клиента. Синтаксис подтверждён официальным parser/константами AWG 3.1.

Если передан `link=1`, для 3.1 строится `vpn://` с `protocol_version: "3.1"`. Ссылка содержит переносимое представление полного `.conf`, поэтому является секретом того же уровня, что и приватный ключ.

## Почему часть полного AWG запрещена

### Header Protection

`HeaderProtectionKey` меняет обработку заголовков. Ключ и логика должны совпадать на клиенте и сервере. Установить ключ на Cloudflare невозможно, поэтому поле отсутствует, а API-override возвращает HTTP 400.

### `S1..S4`

Ненулевые значения добавляют AWG-паддинг перед типами сообщений. Обычный WireGuard peer ожидает сообщение без такого префикса, поэтому все четыре поля равны нулю.

### `H1..H4`

Полный AWG позволяет менять номера типов, если обе стороны настроены одинаково. Cloudflare изменить нельзя, поэтому сохраняются стандартные `1,2,3,4`.

### Random Trailers и cookies

Случайные хвосты должен обработать AWG 3.1 peer. Cookie Reply зависит от состояния сервера. Для неподконтрольного stock-WireGuard peer доступны только стандартные варианты.

### Почему нет переключателя «всё равно включить»

Он создавал бы современно выглядящий, но вероятно нерабочий файл. Защита действует на всех уровнях:

- полей нет в UI;
- GET/POST overrides отклоняются;
- шаблоны не могут их включить;
- mobile/router не меняют wire-format;
- перед сериализацией значения нормализуются повторно.

## Экспериментальный `ContentPaddingAddition`

Механизм добавляет случайный объём дополнительного паддинга. Upstream относит его к клиентской стороне, но рекомендует согласованную поддержку сторон для предсказуемой работы. Поэтому для WARP он не включён автоматически.

Правила 2.7.0:

- по умолчанию строки в `.conf` нет;
- переключателя в основном UI нет;
- нужен API opt-in `experimentalContentPadding=true`;
- default после opt-in — `10-100`;
- свой диапазон передаётся как `contentPaddingAddition`;
- API всегда возвращает interoperability warning.

```http
GET /api/warp?mode=awg31&experimentalContentPadding=true&contentPaddingAddition=10-40
```

Для отключения нужно убрать opt-in или передать ложное значение. `contentPaddingAddition=off` при включённом opt-in не отключает эксперимент: текущая нормализация применит default `10-100`.

При любой проблеме импорта, handshake или трафика сначала повторите генерацию без Content Padding.

| Среда | Причина |

## Генерация, импорт, handshake и трафик — разные проверки

1. **Генерация:** Cloudflare выдал регистрацию, генератор построил ответ.
2. **Импорт:** конкретный клиент распознал поля.
3. **Handshake:** UDP доступен, клиент и Cloudflare согласовали WireGuard-сессию.
4. **Трафик:** маршруты, DNS, IPv4/IPv6 и MTU подходят сети.

Успех предыдущего шага не доказывает следующий. Файл может создаться, но старый клиент отклонит range; импорт может пройти, но провайдер заблокирует UDP; handshake может быть, но сайт не входит в `AllowedIPs` split-туннеля.

При автоматическом выборе IP выполняется TCP-предпроверка endpoint. Она отбрасывает явно плохих кандидатов, но **не является UDP-пробой и не подтверждает WireGuard/AWG handshake**.

## Endpoint и порты Cloudflare

WARP-шаблоны проекта по умолчанию используют `engage.cloudflareclient.com:4500`.

Текущая документация Cloudflare подтверждает WireGuard UDP:

- `2408` — основной;
- `500`, `1701`, `4500` — fallback.

Источник: [Cloudflare One — Required network traffic](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/deployment/firewall/).

Allowlist проекта также сохраняет `880` и `8854` для обратной совместимости. Текущая документация Cloudflare не подтверждает их как актуальные WireGuard fallback-порты, поэтому новую диагностику лучше начинать с `2408`, `4500`, `500`, `1701`.

Полный `peerEndpoint` имеет приоритет. Допустимы IPv4 `203.0.113.10:2408` и IPv6 `[2001:db8::1]:2408`; доменное имя в override не принимается, доменный endpoint задаётся шаблоном.

## Маршрутизация и IPv6

### Full tunnel

Без пресетов или при `routeMode=full`:

```ini
AllowedIPs = 0.0.0.0/0
```

IPv6 по умолчанию выключен; `ipv6=1` добавляет IPv6-адрес и маршруты, когда это допускает профиль.

### Split tunnel

`routeMode=split` требует хотя бы один preset. Домены и статические списки разрешаются в CIDR и только они попадают в `AllowedIPs`. Пустой split отклоняется HTTP 400, чтобы не создать формально подключающийся, но ничего не маршрутизирующий файл.

IPv4-only по умолчанию уменьшает число маршрутов и лучше переносится мобильными и роутерными таблицами. Это не запрет IPv6 в WARP — его нужно включить осознанно.

---

## Mobile и router

`mobile=1` задаёт `Jc=3`, `Jmin=64`, `Jmax=128`, `MTU=1280` и принудительно отключает IPv6, даже при `ipv6=1`.

`router=1` ограничивает `Jc` максимумом `2`, `Jmin` диапазоном `40..128`, `Jmax` максимумом `128`. Это снижает нагрузку, но **не устанавливает AWG на роутер**.

При `mobile=1&router=1` сначала применяется mobile, затем более строгие router-ограничения: итоговый `Jc` равен `2`. Для AWG 3.x API помечает такую совместимость `experimental/router-dependent`.

## Форматы и интерфейс

### `.conf`

- AWG 3.0: `AmneziaWarp-AWG3.0.conf`;
- AWG 3.1: `AmneziaWarp-AWG3.1.conf`.

Интерфейс скачивает первый файл и показывает повторное скачивание, просмотр и объяснение результата.

`count=2` или `3` создаёт отдельные WARP-регистрации и файлы `_variant1..3`. По возможности выбираются разные `/24` endpoint-подсети. Автоматически скачивается только первый вариант, остальные доступны кнопками, поскольку браузеры блокируют несколько программных загрузок подряд.

### `vpn://`

- AWG 3.1: при `link=1`, протокол `3.1`;
- AWG 3.0: отсутствует даже при `link=1`, возвращается warning;
- UI запрашивает ссылку автоматически: у 3.1 кнопка копирования появляется, у 3.0 скрыта.

### QR и сторонние форматы

QR помечен экспериментальным и зависит от `vpn://`; отдельного стабильного QR-экспортера/кнопки в основном UI нет. Для AWG 3.0 QR через `vpn://` невозможен.

Статусы sing-box/Mihomo/Clash/OpenWrt в карточке — это честная карта будущих или ручных путей, а не готовые экспортеры. Стабильный результат 2.7.0 — `.conf`, плюс `vpn://` там, где он реально построен.

## API AWG 3.x

```http
GET /api/warp
POST /api/warp
```

Параметры принимаются из query или JSON POST. `content` содержит `.conf` в base64; ответ также может содержать `configs`, `mode`, route metadata, `appliedExtras`, `compatibility`, `warning` и объект `awg`.

### Режимы и aliases

| Режим | Значения `mode` |
|---|---|
| 3.0 | `awg3`, `awg3.0`, `awg30`, `3`, `3.0`, `v3`, `v3.0` |
| 3.1 | `awg31`, `awg3.1`, `3.1`, `v3.1`, `31` |

Неизвестное значение сохраняет историческое поведение нормализатора и становится legacy. Интеграциям следует использовать канонические `awg3`/`awg31`, чтобы опечатка не была скрыта.

### Шаблоны

- 3.0: `warp_amnezia_awg3`, `amnezia_awg3`, `awg3_amnezia`, `warp_awg3_amnezia`;
- 3.1: `warp_amnezia_awg31`, `amnezia_awg31`, `awg31_amnezia`, `warp_awg31_amnezia`.

Шаблон задаёт режим, engage-host, порт проекта, встроенный `I1` и plain-address, но не может включить запрещённые поля.

### Параметры

| Параметр | Формат | Default |
|---|---|---:|
| `rekeyAfterTime` | integer / `min-max` | `100-120` |
| `rekeyTimeout` | integer / `min-max` | `3-7` |
| `rejectAfterTime` | integer / `min-max` | `150-180` |
| `keepaliveTimeout` | integer / `min-max` | `5-15` |
| `maxHandshakeAttempts` | integer / `min-max` | `15-20` |
| `persistentKeepalive`, `keepalive` | integer / `min-max` / `off` | `25-35` |
| `experimentalContentPadding` | opt-in boolean-like | off |
| `contentPaddingAddition` | integer / `min-max` после opt-in | `10-100` |
| `i1`, `i1Ref`, `cps5` | CPS-настройки | template / off |
| `mobile`, `router`, `ipv6`, `link` | boolean-like | off; UI передаёт `link=1` |
| `count` | `1..3` | `1` |

Строгий parser допускает десятичные целые `0..65535` и неубывающие диапазоны. Отклоняются дроби, scientific/hex notation, обратные диапазоны, внутренние пробелы, лишние символы, переносы строк, инъекции и небезопасные целые.

### Примеры

```http
GET /api/warp?mode=awg3&routeMode=full&persistentKeepalive=25-35
```

```http
POST /api/warp
Content-Type: application/json

{
  "mode": "awg31",
  "routeMode": "full",
  "link": true,
  "rekeyAfterTime": "100-120",
  "rekeyTimeout": "3-7",
  "rejectAfterTime": "150-180",
  "keepaliveTimeout": "5-15",
  "maxHandshakeAttempts": "15-20",
  "persistentKeepalive": "25-35"
}
```

Запрос `?mode=awg31&RandomTrailers=on` вернёт HTTP 400. Аналогично блокируются `headerProtectionKey`, `disableCookies`, `S1..S4`, `H1..H4` — даже с внешне безопасным значением, потому что это не публичные overrides.

`awg` metadata сообщает версию, профиль `warp-safe`, peer `stock-wireguard`, разрешённые/запрещённые функции с причинами, эксперименты, доступность `vpn://` и router-статус. Приватный ключ, `.conf`, CPS и payload ссылки туда не попадают.

## Диагностика

### Ошибка до скачивания

Причины: Cloudflare registration API, неполный ответ, неизвестный preset, пустой split, запрещённый порт, неверный диапазон или заблокированный AWG override. Клиент ещё не участвует.

### Файл не импортируется

Вероятнее всего parser устарел. Обновите клиент до подтверждённой версии. Если нельзя — сгенерируйте AWG 2.0/Legacy; ручное удаление строк не является корректной конвертацией 3.x.

### Импорт есть, handshake нет

1. Отключите Content Padding.
2. Убедитесь, что вручную не изменены H/S, trailers, cookies, Header Protection.
3. Проверьте UDP и попробуйте `2408`, `4500`, `500`, `1701`.
4. Создайте другой вариант/endpoint.
5. Убедитесь, что клиент исполняет AWG 3.x, а не игнорирует поля.

### Handshake есть, сайты не открываются

Проверьте `AllowedIPs`, full/split, DNS, IPv6, локальный firewall, MTU и актуальность route lists.

### Работает на ПК, но не на телефоне

Используйте `mobile=1`, IPv4-only, один вариант, без padding. Проверьте точную версию приложения.

### Работает в приложении, но не на роутере

Роутеру нужен AWG 3.x runtime/parser. `router=1` только уменьшает junk и не добавляет поддержку протокола.

### Нет `vpn://` у AWG 3.0

Это намеренное ограничение. Используйте `.conf`.

## Рекомендуемый первый запуск

1. Обновить подтверждённый клиент.
2. Выбрать 3.1 для `vpn://` или 3.0 для требуемого `.conf` 3.0.
3. Начать с full tunnel, IPv4-only, одного варианта и defaults.
4. Не включать Content Padding.
5. Проверить импорт, затем handshake, DNS и сайты.
6. Только после базового успеха включать split, IPv6, `cps5`, несколько вариантов или эксперимент.

Так проще понять, какой слой отказал.

## Безопасность

- `.conf` содержит приватный ключ; его нельзя публиковать или прикладывать к issue.
- `vpn://` содержит эквивалентный секретный профиль.
- QR из такой ссылки тоже является секретом.
- Каждый вариант имеет отдельную регистрацию и ключи.
- Compatibility/AWG metadata не копирует ключи, конфиг и payload ссылки.
- На общем компьютере удалите файлы и локальную историю интерфейса после переноса.

## Обратная совместимость

- Legacy и AWG 2.0 остаются доступны.
- API-поля 2.7.0 добавлены без удаления прежнего контракта.
- Первый из нескольких конфигов по-прежнему дублируется в `content`; все находятся в `configs`.
- 3.1 — не «2.0 плюс две строки»: нужен 3.x parser/runtime.
- Для 3.0 нельзя подставлять наугад `protocol_version=3` или `3.0`; используется доказуемый `.conf`.
- Для старой среды нужно генерировать старый режим заново, а не вручную урезать 3.x.

## Проверки и предел доказательств

Автотесты покрывают aliases/templates, порядок полей, H/S-инварианты, отсутствие Header Protection, флаги 3.1, defaults/overrides, строгий parser, HTTP 400, GET/POST, `vpn://` 3.1, отсутствие ссылки 3.0, padding warning, `count=3`, CPS5, mobile/router, IPv6, маршруты, UI, локализацию и secret-free metadata. - handshake из каждого региона и устройства;

- долгосрочное поведение батареи.

Релиз гарантирует контракт генератора и WARP-safe границы, но не обещает проходимость любой сети.

## Частые вопросы

### Cloudflare теперь поддерживает AWG 3.1?

Нет. Клиент выполняет допустимые AWG-функции, Cloudflare получает стандартный WireGuard wire-format.

### Чем это полезнее обычного WireGuard?

Junk/CPS и непостоянные таймеры меняют наблюдаемый рисунок клиентского трафика без установки AWG на Cloudflare.

### Это гарантирует обход блокировки?

Нет. Результат зависит от DPI, UDP-портов, endpoint, сети и клиента.

### Почему нельзя включить весь AWG 3.1?

Header Protection, нестандартные H/S, trailers и cookie-obfuscation требуют согласованного AWG peer на сервере.

### Почему 3.0 без ссылки?

Для 3.1 `protocol_version: "3.1"` подтверждён официальным кодом; для исторического 3.0 подтверждения нет. Генератор не угадывает.

### Откроет ли файл обычный WireGuard?

Надёжно — нет: файл содержит AWG-поля и диапазоны, которые обычный parser не обязан принимать.

### Можно ли вручную включить Header Protection?

Файл отредактировать можно, но Cloudflare не получит ключ/настройку. Вероятный итог — отсутствие handshake.

### Что выбрать?

- AWG 3.1 — актуальный клиент и `vpn://`;
- AWG 3.0 — клиенту нужен именно 3.0 и импорт `.conf`;
- AWG 2.0/Legacy — среда не поддерживает 3.x.

## Известные ограничения 2.7.0

- Нет собственного AWG-сервера и UDP handshake probe.
- Нет серверной Header Protection, нестандартных H/S, trailers и cookie-obfuscation.
- Content Padding — API-only эксперимент.
- Нет стабильных экспортеров sing-box/Mihomo/Clash/OpenClash/HomeProxy/OneBox.
- Нет готового нативного AWG 3.1-пакета для роутеров.
- Нет подтверждённого `vpn://` 3.0.
- QR не является стабильным отдельным UI-экспортом.
- TCP pre-check не доказывает UDP/WireGuard.
- Совместимость определяется точной версией parser/runtime, а не названием клиента.

## Итог

Release 2.7.0 вводит проверяемый контракт AWG 3.0/3.1 поверх WARP: клиентские механизмы включены, стандартный WireGuard wire-format сохранён, серверные функции заблокированы, импорт создаётся только при подтверждённой версии, а эксперименты явно помечены.

Это максимальный безопасный объём AWG 3.x-функций, который можно применить к Cloudflare WARP, не выдавая обычный WireGuard peer за полноценный AWG-сервер.
